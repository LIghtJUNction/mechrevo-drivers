## 状态如何更新

每个功能分别记录 Linux、Windows 的**读取、写入、写后回读、失败恢复、测试、安装、加载与实体效果**。内核源码有接口、软件能读回请求值、设备真的改变，属于不同证据；模拟或离线测试不能填入实体通过。未知、未实现、接线中、已安装但未加载、待配件验证也分别保留。

基线 Rust 控制台已有系统电源策略、屏幕亮度后端及遥测／目录／导出，OEM 控制尚未接入。基线收据记录 Linux 驱动和控制台 r158 已安装，核心仍运行 r106，新内核代码待重启验收；Windows 只有编译与产物记录，没有实机验收。这些是基线收据事实，不是本页编写时重新读取的运行状态。[部署收据](verification/deployment-r158.json)、[控制台边界](MECHREVO-CONSOLE.md)

本轮 OEM 后端、CLI／GUI 与受限提权通路正在接线，统一标为 `implementation_in_progress`。代码合入后仍需分别更新源码、测试、安装加载及实机证据，不能提前把下表改成完成。不计算没有明确分母和硬件范围的“迁移百分比”。

## 先实现什么

1. **已有驱动能力接入。** 只枚举实际暴露的接口，优先充电档位、背光与 Fn 锁；USB／接电开机先完成支持判定。CLI、GUI 和受限 helper 共用计划、校验、写入、回读与条件恢复，不添加通用任意路径或寄存器写入入口。
2. **OEM 模式和风扇事务。** 取得范围与所有权依据，完成双通道、部分失败、恢复及事件回归，再在正确加载版本上验证真实曲线、噪声和负载。
3. **原生遥测与资源验收。** GPU 身份、无谓唤醒、陈旧值与长时间资源数据一起完成；重写框架本身不是资源改善证明。
4. **日用控制面。** 托盘／OSD／快捷键、AC/DC 记忆、应用方案、显示和外设开关逐项接入。
5. **Windows 同契约后端。** 单独完成设备绑定、驱动 ABI、权限与读写／恢复；不以 Linux 结果或 Windows 编译替代。
6. **BLE 与固件功能。** 按确切控制器、配件和固件补协议与实体验收，继续计入未完成范围。
