## 原始 51 版客户端、托盘与服务链

已从原始安装 ZIP 的 5.17.51.34 MSIX bundle 核对实际 `ControlCenter3` 应用身份。
`ControlCenterU.exe` 与 `GamingCenterU.exe` 是启动器，不能把它们当成全部 UI。
真正主界面 `GamingCenter3_Cross.dll` 无 CLR header，属于 native AOT；其控件逻辑尚未闭合。
同一包中的 `SystrayComponent.exe` 才是本次分析的托盘客户端；broker 为 `GCUBridge.exe`。
全程只分析冻结文件，没有启动原厂程序、连接 broker 或实测 Windows 操作。

已闭合的一条静态链为：

1. 托盘 Gaming 菜单处理器 `0x0600001c` 发布 `Fan/Control`，
   JSON 的 Action 为 `OPERATING_GAMING_MODE`，没有显式 ProfileIndex。
2. 客户端使用本机 MQTT 端口 13688、QoS 2，经 broker 的订阅投递到服务；
   broker 自己的其他服务控制/固件消息处理器不能当成风扇请求消费者。
3. 服务启动绑定消息回调 `0x0600123e`，经 `0x0600123f` 分派到
   `MyFanCtrl.Receive`（`0x06000ec9`）。已限定的本机分支选择 RamFan1p5，
   实际异步处理体为 `0x0600173c`。
4. 未提供 ProfileIndex 时采用当前 GamingProfileIndex，再经 `0x0600172d` 排队模式 worker，
   `0x06001742` → `0x0600172c` → `0x060016df` → `0x06001700` 应用所选 profile。
5. 服务 `0x060016d2` 发布 `Fan/Status`；托盘消息/界面状态处理器
   `0x060001f0`、`0x060001d6` 更新菜单和图标。另有独立 `Tray/Status` 通道。

**菜单变更或 MQTT 送达不能证明硬件应用成功。** 服务接收入口是 async void，
状态回传无逐请求硬件成功/失败关联；一个即时状态可能早于异步模式应用完成。
客户端离线/发布失败会排队，重连后重发；所检查链中未见逐命令过期/替代规则或应用完成 ACK。
服务发布异常和托盘解析/渲染异常会记录日志，不能把软件配置状态当作 EC/GPU/曲线事务的成功回读。
这是静态失败边界，不是已复现的 Windows 运行故障。

另在 native AOT 的 AC payload 发布链确认 QoS 2、retain=false 及离线 enqueue 路径，
冻结证据保留在私有 `mapping/aot-ac-publish-followup`。这只闭合发布行为；
枚举 42/43 的名称、JSON 字段、编码及服务端应用 ACK 仍未闭合，不证明 AC 功能已支持或应用成功。

Turbo/项目属性的菜单显示还取决于注册表和 Customize/SupportInfo；
本轮没有本机 Windows 注册表或实际显示快照。托盘链不包含主 UI 的 USB/AC 控件，
不能用它宣布这两项客户端支持判定已闭合。
Linux 后续应提供有界、可过期/合并的待执行命令、请求 ID、实际应用后结果、
离线及部分失败反馈；这些是待实现的产品要求，不是已完成改动。

## 动态字符串与 EFI 格式的新边界

字符串解码入口 `0x0600196f` 经 `0x0600182f` 创建 DynamicMethod，不走 native netvm。
实际载荷为 75 字节方法帧，其中 63 字节 CIL、35 条指令；独立有界静态模型的
72 组用例覆盖空值、空串、UTF-16、回绕和长度边界，没有执行 OEM/CLR 动态方法。
已从原始 `#US` 堆静态恢复 3,320 个唯一字符串，关联 10,965 个相邻载入/调用位置。
此范围是已有原始/恢复 IL 中相邻 `ldstr` 后调用该解码器的记录，不能扩展为全部动态字符串或全部配置逻辑。
完整语料、OEM 指令、解密参数仍私有；六个已定位动态载荷已恢复，但不覆盖 native VM 的真实 program 映射。

OEM 51 的 EFI managed 结构为 188 字节，本机变量实际 payload 为 180 字节；
原厂读取有零填充尾部的行为，不证明两者 ABI 兼容。受限只读前缀诊断中，
APVersionCheck、ACRecoverySupport、ACRecoveryStatus 对应位置均读到 0，
回执明确为 `format_qualified=false`。因此不能据此最终判定 AC 开机不支持，
更不能把该诊断作为完整结构、版本或 EFI 写入资格证明。本轮没有 EFI 写入。

## 通用设置的支持与持久化边界

下列结论来自原始 51 版静态方法及已恢复字符串，没有执行 Windows 设置或复现运行故障。
`GetFwVarsSecond`（`0x06000b39`）只是 `APVersionCheck=0` 后的重试：仍调用相同
188 字节结构的读取和转换，没有项目号、版本或 180 字节布局协商。因此前缀字段可见、
重试存在和 UI 显示都不能提高当前 EFI 格式的验证等级。

支持信息生成方法 `0x06000b11` 将 `AcRecoverySwitchSupport` 硬编码为 1，
将 `AcRecoverySwitchBiosSupport` 取自 EFI 支持字段，再由 `0x0600129c` 导出给客户端。
通用 manager 仅在 EFI 支持字段等于 1 时走 NVRAM 设置，其余情况回退到 `0x0726` bit 3。
这证明两种控制分支存在，不能证明本机冷接电开机适用；UI 的 1 也不能代替硬件支持证据。
USB 的 `0x0767` bit 4、注册表状态和启动重放已确认，硬件支持与独立客户端可见性仍未闭合。
本轮没有据此加入 GM6 允许名单或执行 EFI/EC 写入。

独立充电阈值属性 setter `0x06000936/0x06000938/0x0600093a` 传给
`SetFwVars`（`0x06000b42`）的三个字段名，不在该重载的完整选择表中。
源码确认它不会更新对应缓存字段，却仍可能提交已有缓存；尚无 Windows 运行复现。
因此不能把这些 void 调用算作持久化成功，也不能把充电模式接口当作上下限功能全部迁移。
Linux 后续实现需保留明确错误、状态回读及恢复，实际停充/恢复与 AC 变化另行验收。

## 电源与显示事件的新证据

原厂 App 初始化实际注册 `SystemEvents.PowerModeChanged`，其普通处理器只处理数值 2，
刷新 AC 状态后调用所选 manager 的 `Init(false)`。Microsoft 定义 Resume=1、
StatusChange=2、Suspend=3，因此这里是电源状态变化处理，不是已证明的挂起回调。
[Microsoft PowerModes 定义](https://learn.microsoft.com/en-us/dotnet/api/microsoft.win32.powermodes?view=netframework-4.8.1)。

默认通知路线实际注册 `GUID_CONSOLE_DISPLAY_STATE`，恢复出的 GUID 与官方常量一致。
该事件的 0/1/2 表示显示关闭/打开/变暗，不能把原厂方法名中的 ModernStandby 当成真正睡眠。
另一条配置选择的路线才注册 Resume 事件，并另有 WMI/EC 状态路线；它的处理器没有区分 S3/S4。
[Microsoft 电源通知 GUID 定义](https://learn.microsoft.com/en-us/windows/win32/power/power-setting-guids)。

恢复后的异步状态机与方法关联由原元数据属性确认。打开/Resume 路线中存在
`Thread.Sleep` 的 3 秒及 2 秒阻塞；其间重载 profile、设置 AP-exists、调用风扇/设置/电池恢复。
这仍不保证异步风扇曲线已提交。关闭路线也不能直接证明已把风扇切回固件自动控制。
这些是静态调用与阻塞证据，不是 Windows 实际时延测量或所有睡眠状态的运行验证。

原厂服务停止仅清表使能；已检查的路径没有排空曲线队列，队列 closure 也没有停止状态检查。
因此源码允许待执行/正在执行的曲线动作在停止后再次使能表控制。
这是尚无 Windows 运行复现的可达交错，外层同步仍可能施加其他限制，不能写成已复现原厂故障。
Linux 应保留明确错误、工作队列屏障和恢复目标，不必复制这些弱点。
新 Linux PM 修复此前的 371 项相关回归通过；remove/rebind 续修另有 167 项定向回归，
完整本地测试现为 724 项通过。r78 已安装到磁盘，但核心仍运行旧版，不能说新修复已经运行生效。显示事件也不构成完整 S3 睡眠证明，

3. 分别核对源码、测试、提交/推送、包发布、安装和运行中的版本，再验证真实物理功能、

4. 使用可比较的任务/环境衡量可靠性、控制响应、温度/性能/噪声及操作体验。
