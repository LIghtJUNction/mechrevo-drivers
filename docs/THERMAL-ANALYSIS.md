# 离线复核温度采样

在仓库根目录运行，无需安装依赖：

```sh
python scripts/analyze_thermal.py /path/to/readable-capture.json
```

这是仓库内的离线分析脚本，尚未加入 `mechrevo-power-control` 安装包。
它只读取指定 JSON、输出结果，不调用 nvidia-smi、EC、服务或功耗接口，也不改写输入。
结果保留输入原始字节的 SHA-256，便于对应具体文件。
输入需要对当前用户可读。退出码 0 只表示分析成功，不代表采样有效；应查看
`capture_checks_passed`。无法识别的结构、错误数值及不一致的计数器返回非零。

支持现有 `mechrevo-thermal` schema v1 和本项目早期的带 labels 的观测文件。
早期文件没有完整的 GPU／日志检查凭据，因此始终为 `capture_checks_passed=false`。
失败、中断、有故障记录、空文件或单样本捕获也不会被提升为通过检查。

输出包括 CPU 温度范围和样本均值、达到 95°C 的样本数量／比例、CPU 与 EC
温度平均绝对差、双风扇原始值范围及不同读值数量、封装热节流计数增量。
平均封装功耗按总能量差除以首末样本时间差计算，不把不等长区间功耗直接平均。
它使用采样时间近似能量读取时间，假设每个区间最多回绕一次；无法区分计数器重置和回绕。
计数回绕范围改变、时间倒退或热节流计数下降会拒绝分析。

至少 10 个近似等间隔样本时，还输出前后 5 个样本的温度平移扫描。
正向平移表示把较晚的 EC 样本与较早的 CPU 样本配对，各行同时保留配对数量。
不等间隔数据不做这个扫描；恒定温度的相关系数为 null。
相关性不能证明传感器物理延迟，各种平移丢弃的端点也不同。

这些是样本统计，不是温度持续时间。风扇原始刻度不是 RPM，也不是已经校准的百分比。
单份文件不能证明优化有效；对照仍需要相近负载、环境、初始散热状态和有效采样。

## 2026-10-16 对历史 90 样本数据的复核

输入为未跟踪的 `research_notes/thermal-observation-20261015.json`，原文件未修改。
结果保存在 `.local-tests/thermal-output-20261016/gpu-guard/legacy-analysis.json`。

- 首末样本相隔约 89 秒，CPU 65–100°C，样本均温约 91.79°C。
- 44/90 个样本达到 95°C，约 48.9%；不能写成 48.9% 的时间都处于高温。
- 近似平均封装功耗 35.47 W，热节流计数增加 5283；计数不是节流时长。
- CPU／EC 温度平均绝对差 3.06°C；在前后 5 个样本的扫描范围内，
  不平移时的相关性最高、平均绝对差最低。这段数据不支持固定数秒延迟的解释，
  也不能排除其他时刻的传感器问题。
- 两路风扇原始读值均为 160–170，各有 8 种不同值；证明有变化，不能证明风扇实际 RPM、
  已到满速或足以及时散热。

该历史文件没有当前观测器的完整检查凭据，因此分析仍标记为未通过检查。
没有据此调整风扇、PL1、PL2 或 EC 参数；显卡仍需用户手动重启恢复后才能开展新的有效对照。
