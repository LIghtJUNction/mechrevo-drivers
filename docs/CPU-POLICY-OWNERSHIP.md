# CPU 策略控制权

当前已复现控制器竞争。**CPU 控制权交接后端已落地源码并通过离线回归，完整控制台交接链尚未完成，也未安装新版 TCC。** 不能靠档位名称已经改变，就声称 CPU 策略能保持生效。

## 已确认的问题

安装版 r177 的普通用户 CLI 已两次完成 `balanced → power-saver → balanced`，四次 Set 均收到明确应答并独立读回；同档位操作不提交 setter，错误的预期当前值在 setter 前拒绝。原有 55W 策略、服务和加载模块身份保持不变。[实测记录](verification/linux-profile-control-r177.json)

同步观察两个服务和两条 CPU sysfs 路径时，捕获到 PPD 成功写入 CPU0 的 EPP `power`／`balance_performance` 和 EPB `15`／`6`。随后 tccd 写入同一 EPP 文件的 `default`，再写 `power`；距 PPD 的平衡值写入约 2.878 秒。24 个策略的快照也显示平衡值随后回到 `power`。这证明两个控制器会覆盖同一项 CPU 设置，不证明风扇机械异响、温控或性能问题的根因。

TCC v3.0.10 的 [CpuWorker](https://raw.githubusercontent.com/tuxedocomputers/tuxedo-control-center/v3.0.10/src/service-app/classes/CpuWorker.ts) 会定期校验并重放 CPU 配置。当前实例启用了 CPU 设置；实测没有修改它的配置或停止服务。被观察的服务仍存活，观察器已脱离；轨迹仅用于上述成功写入的正面证据，不据此声称没有其他写入者。

## 必须实现的交接

1. 用户明确预览“交给系统电源服务”或“交还 TCC”。预览分别列出 CPU 控制权变化和档位变化；读状态与刷新不提权、不自动接管。
2. 在 TCC 增加只作用于 CPU worker 的窄接口。交接确认后，该 worker 的启动、周期校验、切档和退出路径都遵守同一个控制权状态。风扇、灯光、充电及其他 worker 不随之重放，不使用全量设置重载来交接。
3. 交接写入由现有普通用户控制台发起明确授权，通过固定位置的受限 helper 调用。新 TCC 写接口仅允许经过系统总线认证的 root 调用；helper 不接受任意设置 JSON、命令、文件路径或服务名。
4. 绑定 TCC 的版本、能力、唯一 owner、设置代次以及磁盘／内存设置摘要。旧版不具备交接接口时明确拒绝接管。写前发现外部修改就拒绝；恢复只处理仍属于本次操作的状态。
5. TCC 的交接应答必须证明原 CPU 写入工作已经结束，之后再向 PPD 提交档位。分别保留交接、Set、读回和持久化结果；第二步失败不能伪造整体成功，也不能自动重试或重建已释放的应用请求。
6. 持久化与运行中状态必须一致，并覆盖重启后的行为。写入或应答不确定时保留原始错误和独立观察；界面显示部分结果与可执行的恢复入口。

## 已实现的 TCC 后端

本地 pkgrel7 配方增加 [`0007-cpu-control-ownership.patch`](../packaging/arch/tuxedo-control-center-mechrevo/0007-cpu-control-ownership.patch)。它在原有 TCC v3.0.10 源码上实现以下接口：

- `GetCpuControlStateJSON() → s`：只读状态、能力版本、进程实例标识、控制权代次及预览 token。读取不创建状态文件，也不重放 worker。
- `SetCpuControlOwner(owner: s, token: s) → s`：只接受 `tcc`／`system` 和仍有效的预览 token。token 同时绑定进程实例、版本、控制权文件身份、磁盘／内存设置摘要、配置加载代次、磁盘设置文件身份及 CPU 档位。重启实例、同内容文件替换或在检查时观察到的外部修改会使旧请求失效。

持久化文件固定为 `/var/lib/tuxedo-control-center/mechrevo-cpu-owner.json`，目录由首次明确交接创建为 root `0700`，文件为 root `0600`。读取检查文件、目录身份、权限、链接数、长度和规范 JSON；缺少文件沿用 TCC 控制，已有文件损坏或不可读时阻止 CPU 写入。写入使用受保护目录描述符、独占临时文件、文件与目录同步、写前重查和独立回读。重命名发生异常时保留“是否提交未知”，不自动覆盖或回滚。写前重查不等于能与任意外部 root 写入者实现原子的文件比较交换。

启动、周期校验、切档后的启动、退出、直接应用及默认配置路径都经过同一个 CPU 写入检查。交给 `system` 时不触发 CPU 或其他 worker 的重放；现有同步 CPU 写入在该事件循环发出交接应答前已经返回。交还 `tcc` 时只调用 CPU 重放，保留用户原本禁用 CPU 设置的选择，并分别报告持久化和 CPU 重放结果。没有可用 CPU 列表时不能报告回读成功。

`cpu_replay.validation_passed` 使用上游现有 CPU 校验器，**不代表每次底层写入均有独立应答**；例如现有校验器会跳过部分 `intel_pstate` 频率检查。它不能替代后续 CPU 偏好、限频等实际读回。CPU 重放失败后，已持久化的控制权仍单独报告，不伪造整体成功。

总线配置声明 root 可调用新 setter，并为普通调用者拒绝该成员的所有路径与接口。实际私有 Unix 总线回归已覆盖普通用户通过常用名、唯一 owner 地址、省略接口名及错误接口名的调用；旧配置会被同一回归抓住。**真实 root 凭据通过总线的成功调用、受限 helper、CLI／GUI 预览与提权、应答丢失后的调用端恢复入口仍未验收或实现。** 客户端还必须独立绑定服务唯一 owner 和 UID；不能只相信状态中的进程标识。

完整配方 `prepare` 后的 437 个源文件字节前后相同，完整 service／e-app TypeScript 检查通过，TCC 统一回归 **78 项、零跳过**，其中新增 CPU 控制权回归 18 项。测试执行真实补丁后的 CpuWorker、D-Bus 类和提取的真实 daemon `main` 方法；硬件、其他 worker 构造与进程权限检查使用测试替身，私有总线使用真实 D-Bus。记录包括旧实现反例和一次真实捕获的空 CPU 列表误报；这不等于重启了真实 TCC。[验证记录](verification/cpu-ownership-backend-pkg7.json)

pkgrel7 **尚未完成生产打包、安装或运行激活**。完整配方的类型检查仅通过只读依赖引用运行；正式生产打包仍需遵守配方 README 的独立依赖目录要求。当前安装的 TCC 仍为 `3.0.10-1`，控制台仍为 r177。
