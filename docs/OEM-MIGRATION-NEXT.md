# 原厂策略迁移：本轮确认的实现边界

2026-10-16；原厂协议部分仅检查已有离线材料，没有执行 OEM 程序或应用新的 EC/风扇策略。
已有控制接口的修复及安装/实机验收状态另行注明。

## 保护层恢复的新证据

原始 5.17.51.34 服务的 5,183 个受保护 CIL 方法体已静态恢复，全部通过独立尾标记检查。
328,357 条指令、20,342 个显式跳转目标的边界检查通过；这不是 CLR 栈/类型验证、
Windows 运行或完整 VM 还原。布局、RPM 和风扇表消费已取得真实指令，详见
[Windows 方法体恢复](OEM-METHOD-BODIES.md)。只发布方法定位、协议事实和校验摘要，
原厂指令、密钥及二进制留在私有证据目录。

## 能立即修复的问题

本轮检查时，`src/uniwill_keyboard.h` 的 `uw_set_fan_locked()` 在 universal
风扇能力成立、但模式字节 `0x0751` 的 `0x40` 位已置位时，会跳过设速操作，
最后返回成功。源码可确认“请求没有执行却报告成功”；尚未在本机主动制造此模式。
现已修复为返回 `EBUSY`，保留该模式与风扇目标；新增真实 C 回归在旧源码上失败，
修复后风扇运行测试 37 项通过。已安装 r61，运行中的 keyboard 仍是 r37，
修复尚待下次重启激活；本轮没有主动制造实机 full fan 冲突。

## 原厂功耗表不是风扇表，也不是已执行的功耗限制

已有本机读数 `PPFG=4`、`GFID=0x11` 对应 `AX44`，这条选择规则已闭合。
但已有 DSDT 中，`AX44` 仅出现于缓冲区声明和 `SMRW` 读写分支：
`SMRW` 的 `0xaa` 分支赋值缓冲区，`0xbb` 分支返回其 DWORD；该方法没有
调用 `T1WR`、写 EC 功耗字段或发 GPU 通知。
因此，不能把“写入原厂参数缓冲区”做成一个声称已应用性能模式的 Linux 按钮。
这不排除 Windows 服务或未分析的其他固件表消费该缓冲区。

复核位置（私有材料，不随 Git 发布）：

- `.local-tests/windows-oem/acpi-host/dsdt.dsl:125645`：12 字节 `AX44` 声明。
- 同文件 `126106`：`SMRW` 请求布局；`126195`：本机阶段分支。
- 同文件 `125875`：`T1WR` 功耗相关入口；`126015`：`PWUP` 策略分支。
- `.local-tests/windows-oem/service-il.txt:31215`：9 字节 Windows 结构体元数据。
- 同文件 `31284`、`31336`：读取、写入方法仍是异常占位，未取得消费逻辑。

`T1WR`、`PWUP`、`PWBT` 的固件实现能说明单个调用的效果，不能反推
Windows 服务的完整初始化、切换、失败补偿和卸载顺序。

## 原厂功耗模式的真实分支与本机默认字节

本机选择的 `MyFanManager_RamFan1p5` 在 Intel 分支中，仅 Custom（mode 3）
将所选 profile 的 PL1/PL2/PL4 转为 byte，写入 `0x0783/0x0784/0x0785`。
Office/Gaming/Turbo（mode 0/1/2）向这三处传入零，表示默认/覆盖请求，不能解释为实测 0 W。
选中 manager 的 PL4 不作 base manager 的减半换算，不能混用两条实现。

TCC 设置对所有模式均检查 profile 开关：启用时将 `offset | 0x80` 转 byte 写 `0x0786`，
禁用写零。OEM 没有在转换前限制范围，Linux 必须验证输入，不能复制 byte 回绕。
写入请求不证明 IA32_TEMPERATURE_TARGET 已改变，也不是本项目的软件 90°C 温控目标。
风扇模式、异步曲线及 CPU/GPU 设置之间没有一个完整原子事务。

默认 profile 会从固件动态刷新，不应把安装包 JSON 中的常量当成本机默认值。
已根据恢复后的 getter 和参数顺序，用固定地址只读探针读取十五个默认字节，三组结果完全相同：

| OEM getter 标签 | PL1 原始字节 | PL2 原始字节 | PL4 原始字节 | DState 原始字节 | TCC 原始字节 |
| --- | --- | --- | --- | --- | --- |
| Gaming | 75 | 75 | 200 | 1 | 5 |
| Office | 45 | 45 | 200 | 1 | 20 |
| Turbo | 130 | 130 | 200 | 1 | 5 |

Gaming 的四字段位于 `0x0730..0x0733`，Office 位于 `0x0734..0x0737`，
Turbo 位于 `0x07a7..0x07aa`；三种 TCC 默认值依次来自 `0x07d8/0x07d9/0x07da`。
这些是 **按 OEM getter 标签解释的固件原始默认字节**，不是观察到的 RAPL 限值、
可安全写入的上下限或已经生效的温度限制。本轮没有功耗/TCC/模式写入。
探针已移除，原模块、服务 PID 和配置保持，期间无新增受监测 GPU/PCIe 故障。
私有来源为 `power-semantics/FINDINGS.md`、`evidence.json`、`mode-matrix.json`
和 `defaults-receipt.json`，均位于 `.local-tests/postboot-20261016/oem-binding/`。

base manager 的 `SetPL124Tau` 实际只转发 PL1/PL2/PL4，忽略 Tau 参数，没有写入时间窗。
这不能推断选中 RamFan1p5 manager 的模式行为，也不能据方法名宣称 Tau 已迁移。
GPU profile 的目标温度另走 GPU 接口，不能用打包 JSON 中的 87°C 代替 CPU 目标。
原厂模式迁移还需闭合实际 profile 选择、编辑/持久化输入及固件接受/恢复路径；
当前 Linux 的 55W 上限和软件 90°C 目标是独立适配策略。

## 本机布局分支已经闭合

真实 `IsSuportRamFan1p5` 读取 `0x078e` bit 6。项目号来自 `0x0740`；
扩展规则只处理 `0x17/0x18`，本机 `0x10` 不变且不在 commercial 项目列表中。
新十组固定地址 ECRR 只读样本均为 `0x078e=0xec`、`0x0740=0x10`，
因此正常读取成功时，OEM 工厂分支选择 `MyFanManager_RamFan1p5` 和 `FanTable_Manager1p5`。
这不是在 Linux 执行 Windows 程序的结果，也不覆盖其他型号/BIOS。

**此前仅凭 STATUS/CTRL 常量别名推测 GPU 末三项可能错写，证据不足，现已纠正。**
恢复后的 Windows `SetEcFanTable` 同样写 16 个 GPU duty，包括 `0x0f5d..0x0f5f`。
这些地址在默认表获取阶段另作握手用途，不能据常量名称缩成 13 项。

实际双表写入每只风扇 47 次、共 94 次：CPU/GPU UpT 起点分别为 `0x0f00/0x0f30`，
前 15 项使用下一档 UpT，末项写 `0xff`；DownT 写 `0x0f11..0x0f1f` 和
`0x0f41..0x0f4f`；16 项 duty 写 `0x0f20..0x0f2f` 和 `0x0f50..0x0f5f`，
值为 duty 乘 2 后转 byte。实际 CIL 的有界符号追踪确认上述顺序；不是实机表写入。

正常提交先清 `0x07c6` bit 2，再按 `FanControlRespective` 更新 `0x07c5` bit 7、
写入曲线，最后请求恢复 `0x07c6` bit 2；只有 `0x0f00/0x0f01` 至少一个非零才置位。
默认表获取是另一个协议：清 `0x0741` bit 0，写 `0x0f5f` 模式及
`0x0f5d=0xfd`、`0x0f5e=0xc9`，每 500 ms 检查一次、至多十次，两个状态均改变才读取。
此处没有对本机试写或触发握手。

OEM 写 API 会吞掉部分锁超时和 I/O 失败，曲线序列没有 finally、完整回读或失败回滚；
15 项短数组可在已写 42 字节后抛异常。Linux 不应复制这种假成功。
服务 Disable/Uninstall 清 `0x07c6` bit 2；Resume 经重新加载 profile 和 Init 恢复，
没有证据证明它恢复先前快照的曲线。完整 OS 事件/异步调用仍未审计完。
现有 Linux universal 手动模式与旧式后台恢复任务的所有权也需分开处理，不能只补一个状态标志。

## RPM 公式与只读实机边界

恢复方法明确 CPU 为 `(ECRR[0x0464] << 8) | ECRR[0x0465]`，
GPU 为 `(ECRR[0x046c] << 8) | ECRR[0x046b]`，无缩放、裁剪或型号分支。
原始元数据常量和 delegate 解析与该公式一致；不能根据地址相邻改用 `0x046d`。
十组本机样本按该公式得到 CPU 3,816–3,878、GPU 4,939。
这是同地址空间的原厂算术值验证，不是物理转速校准或风扇响应验收。
后续 Linux 只读 RPM 模块已完成临时加载/读取/卸载及原模块恢复，再完成 r72 正式安装和独立加载。
运行传感器 build ID 与安装文件一致，`sensors` 已显示双风扇 RPM；机械转速仍未独立校准。

Windows 两次读取复用一个 ref byte，第二次失败可能复用第一字节；底层还存在吞错。
Linux 只读实现已加入明确读取错误及高/低/高字节有界一致性重试，相关失败与边界由回归覆盖。
提交 `749949a` 的临时实机试用通过，完整本地测试 689 项通过；仍不构成机械转速校准。
Linux 曲线提交也已按关闭、写表、启用顺序补齐失败处理，风扇运行回归 53 项通过，
失败路径保留独立错误日志。这里的曲线验证为模拟 EC，未在本机试写风扇表。

## 设置支持判定与持久化的新证据

以下是原始 51 版的静态源码结论，没有执行 Windows 设置或复现其运行故障。
`MySettingCtrl` 的工厂方法 `0x06000f8a` 在已检查的全部分支均选择通用
`MySettingManager`，不能据 Intel CPU 改用另一个 manager 的协议。

EFI 前缀中的 `APVersionCheck=0` 不会选择旧格式：`GetFwVars`（`0x06000b38`）
等待后调用 `GetFwVarsSecond`（`0x06000b39`），后者仍按同一 188 字节结构读取、转换，
没有项目号、版本或 180 字节布局分支。原厂零填充与重试不能消除本机 180 字节 payload
和该结构的差异；现有前缀诊断保持部分验证，不能补零后宣称兼容或据此开放 EFI 写入。

AC 开机的普通 UI 支持值与 BIOS 支持值不同。`0x06000b11` 把
`AcRecoverySwitchSupport` 固定写为 1，把 `AcRecoverySwitchBiosSupport` 取自 EFI 字段；
`0x0600129c` 再向客户端导出这两个值。通用设置初始化只在 EFI 支持字段等于 1 时走
NVRAM 路线，否则读取 `0x0726` bit 3。这个回退状态位和 UI 的 1 都不能证明本机冷接电开机能力。
USB 设置已确认使用 `0x0767` bit 4、注册表状态及启动重放，但选中服务路径没有闭合
GM6 的硬件支持判定，独立客户端的可见性规则也未全部审计；两项 Linux 允许名单保持不变。

充电阈值的持久化另有源码不一致：属性 setter `0x06000936/0x06000938/0x0600093a`
调用 `SetFwVars`（`0x06000b42`），所传三个字段名不在该重载的完整选择表中。
它不会因此更新对应缓存字段，却仍可能提交已有缓存；不能把 void 调用当作阈值持久化成功。
充电模式、独立上下限及其实际停充/恢复仍须分别验证；这是源码确认的问题，尚无 Windows 运行复现。
