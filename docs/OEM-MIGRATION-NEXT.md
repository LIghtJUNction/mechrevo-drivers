# 原厂策略迁移：本轮确认的实现边界

2026-10-16；原厂协议部分仅检查已有离线材料，没有执行 OEM 程序或应用新的 EC/风扇策略。
已有控制接口的修复及安装/实机验收状态另行注明。

## 保护层恢复的新证据

原始 5.17.51.34 服务的 5,183 个受保护 CIL 方法体已静态恢复，全部通过独立尾标记检查。
328,357 条指令、20,342 个显式跳转目标的边界检查通过；这不是 CLR 栈/类型验证、
Windows 运行或完整 VM 还原。布局、RPM 和风扇表消费已取得真实指令，详见
[Windows 方法体恢复](OEM-METHOD-BODIES.md)。只发布方法定位、协议事实和校验摘要，
原厂指令、密钥及二进制留在私有证据目录。

## 能立即修复的问题

本轮检查时，`src/uniwill_keyboard.h` 的 `uw_set_fan_locked()` 在 universal
风扇能力成立、但模式字节 `0x0751` 的 `0x40` 位已置位时，会跳过设速操作，
最后返回成功。源码可确认“请求没有执行却报告成功”；尚未在本机主动制造此模式。
现已修复为返回 `EBUSY`，保留该模式与风扇目标；新增真实 C 回归在旧源码上失败，
修复后风扇运行测试 37 项通过。已安装 r61，运行中的 keyboard 仍是 r37，
修复尚待下次重启激活；本轮没有主动制造实机 full fan 冲突。

## 原厂功耗表不是风扇表，也不是已执行的功耗限制

已有本机读数 `PPFG=4`、`GFID=0x11` 对应 `AX44`，这条选择规则已闭合。
但已有 DSDT 中，`AX44` 仅出现于缓冲区声明和 `SMRW` 读写分支：
`SMRW` 的 `0xaa` 分支赋值缓冲区，`0xbb` 分支返回其 DWORD；该方法没有
调用 `T1WR`、写 EC 功耗字段或发 GPU 通知。
因此，不能把“写入原厂参数缓冲区”做成一个声称已应用性能模式的 Linux 按钮。
这不排除 Windows 服务或未分析的其他固件表消费该缓冲区。

复核位置（私有材料，不随 Git 发布）：

- `.local-tests/windows-oem/acpi-host/dsdt.dsl:125645`：12 字节 `AX44` 声明。
- 同文件 `126106`：`SMRW` 请求布局；`126195`：本机阶段分支。
- 同文件 `125875`：`T1WR` 功耗相关入口；`126015`：`PWUP` 策略分支。
- `.local-tests/windows-oem/service-il.txt:31215`：9 字节 Windows 结构体元数据。
- 同文件 `31284`、`31336`：读取、写入方法仍是异常占位，未取得消费逻辑。

`T1WR`、`PWUP`、`PWBT` 的固件实现能说明单个调用的效果，不能反推
Windows 服务的完整初始化、切换、失败补偿和卸载顺序。

## 本机布局分支已经闭合

真实 `IsSuportRamFan1p5` 读取 `0x078e` bit 6。项目号来自 `0x0740`；
扩展规则只处理 `0x17/0x18`，本机 `0x10` 不变且不在 commercial 项目列表中。
新十组固定地址 ECRR 只读样本均为 `0x078e=0xec`、`0x0740=0x10`，
因此正常读取成功时，OEM 工厂分支选择 `MyFanManager_RamFan1p5` 和 `FanTable_Manager1p5`。
这不是在 Linux 执行 Windows 程序的结果，也不覆盖其他型号/BIOS。

**此前仅凭 STATUS/CTRL 常量别名推测 GPU 末三项可能错写，证据不足，现已纠正。**
恢复后的 Windows `SetEcFanTable` 同样写 16 个 GPU duty，包括 `0x0f5d..0x0f5f`。
这些地址在默认表获取阶段另作握手用途，不能据常量名称缩成 13 项。

实际双表写入每只风扇 47 次、共 94 次：CPU/GPU UpT 起点分别为 `0x0f00/0x0f30`，
前 15 项使用下一档 UpT，末项写 `0xff`；DownT 写 `0x0f11..0x0f1f` 和
`0x0f41..0x0f4f`；16 项 duty 写 `0x0f20..0x0f2f` 和 `0x0f50..0x0f5f`，
值为 duty 乘 2 后转 byte。实际 CIL 的有界符号追踪确认上述顺序；不是实机表写入。

正常提交先清 `0x07c6` bit 2，再按 `FanControlRespective` 更新 `0x07c5` bit 7、
写入曲线，最后请求恢复 `0x07c6` bit 2；只有 `0x0f00/0x0f01` 至少一个非零才置位。
默认表获取是另一个协议：清 `0x0741` bit 0，写 `0x0f5f` 模式及
`0x0f5d=0xfd`、`0x0f5e=0xc9`，每 500 ms 检查一次、至多十次，两个状态均改变才读取。
此处没有对本机试写或触发握手。

OEM 写 API 会吞掉部分锁超时和 I/O 失败，曲线序列没有 finally、完整回读或失败回滚；
15 项短数组可在已写 42 字节后抛异常。Linux 不应复制这种假成功。
服务 Disable/Uninstall 清 `0x07c6` bit 2；Resume 经重新加载 profile 和 Init 恢复，
没有证据证明它恢复先前快照的曲线。完整 OS 事件/异步调用仍未审计完。
现有 Linux universal 手动模式与旧式后台恢复任务的所有权也需分开处理，不能只补一个状态标志。

## RPM 公式与只读实机边界

恢复方法明确 CPU 为 `(ECRR[0x0464] << 8) | ECRR[0x0465]`，
GPU 为 `(ECRR[0x046c] << 8) | ECRR[0x046b]`，无缩放、裁剪或型号分支。
原始元数据常量和 delegate 解析与该公式一致；不能根据地址相邻改用 `0x046d`。
十组本机样本按该公式得到 CPU 3,816–3,878、GPU 4,939。
这是同地址空间的原厂算术值验证，不是物理转速校准或风扇响应验收；尚未增加安装中的 RPM 接口。

Windows 两次读取复用一个 ref byte，第二次失败可能复用第一字节；底层还存在吞错。
Linux 只读移植必须明确传回读取失败，并对跨字节刷新作有界一致性重试，不能以 0 RPM 隐藏错误。

## 下一步的具体交付条件

1. 将已恢复的 ECRR 转速公式做成受限机型/BIOS 的只读接口，验证字节一致性、错误传播、
   边界和卸载生命周期，再核对本机安装、加载及运行状态。
2. 按真实启用顺序修正 Linux 表提交，补齐部分失败、自动模式恢复、读回和并发测试。
   完成恢复材料和安全边界后才安排硬件写入；不能把静态 94 次符号写入算作硬件验收。
3. 分清 universal 手动控制与 legacy 定时恢复的状态所有权，覆盖失败、自动/全速切换和睡眠恢复；
   仍需真实睡眠/唤醒、原厂曲线效果及长期负载验收。
4. 继续追 SMRW 参数消费、功耗字段编码/范围及剩余 VM 分派逻辑。
   已恢复方法总数不代表 Windows 全部功能和所有依赖程序集已分析完。

本轮没有改变安装中的 r11 温控策略、内核核心模块或风扇曲线；100°C 热尖峰仍未解决。
功能验收估计保持原值，不能宣称散热已优于 Windows。
