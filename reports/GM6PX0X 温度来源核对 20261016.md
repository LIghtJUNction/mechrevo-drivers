# GM6PX0X MRO07 温度来源核对

本轮并行静态调查确认：CPU 内部温度、OEM 扩展 EC 温度和 ACPI 热区是不同读取路径。
还不能由温差认定寄存器错误或刷新延迟，也没有据此改风扇曲线。

## 三种信号必须分开

| 来源 | 已确认读取路径 | 未确认部分 |
| --- | --- | --- |
| coretemp CPU Package | Intel 内部温度接口 | 与 EC 信号的刷新先后关系 |
| 驱动 EC CPU/GPU 字节 | 本机 DSDT 将扩展地址 0x043e 命名 CPTM、0x044f 命名 VGAT；tuxedo_io 直接返回字节 | 传感器位置、平滑与刷新周期 |
| ACPI ECTZ 热区 | EmbeddedControl 区域 0x3e 低7位 XHPP，经 _TMP 转成十分之一开尔文 | 与 CPTM 是否共享物理传感器、更新机制 |

EmbeddedControl 0x3e 和 OEM 扩展地址 0x043e 不能仅凭数字相似就视为同一寄存器。
本机 DSDT SHA-256：`de42c0d802ed746c1d032bf53ebb3b80f92172b8fb55e115b0e433566f542cda`。
私有反编译定位：ECMG 字段 127675–127678，ECXP/XHPP 127843–127870，ECTZ 128723–128750。

## ECTZ 返回值不全是普通温度采样

正常分支返回 `2732 + XHPP × 10`。
参考 [Linux ACPI 热驱动](https://github.com/torvalds/linux/blob/master/drivers/acpi/thermal.c)
的转换与偏移选择：本机 _CRT=3732，采用273200毫摄氏度偏移时，显示值就是 XHPP°C。
特殊分支为：

- ECON=0：返回3010，对应27.8°C。
- THOT置位：清零THOT，返回4000，对应126.8°C。
- _Q27会置位THOT并通知热区。

所以极高的 ECTZ 返回值可能包含一次热事件语义，不能直接等同内部传感器真实达到126.8°C。
主动调用 _TMP 会消费该事件标志，不是完全无副作用的读方法。
读取现有 thermal sysfs 也可能由内核求值 _TMP；本轮没有额外主动调用 ACPI 方法。
以上换算是静态协议分析，未人为触发这些分支。

调查时顺序读取：ECTZ 95°C、TZ00 95°C、TCPU_PCI 95°C、x86_pkg_temp 96°C，
随后 coretemp Package 95°C。它们不是同步样本；TZ00 定义不在已反编译的 DSDT，
不能把两个 acpitz 名称归并成 ECTZ。未见“固定60°C”的证据。

## Windows 端能确认和不能确认的部分

原厂 CPUInfo 元数据包含 PerformanceCounter、Thermal Zone Information、Temperature，
但消费方法仍受保护，不能证明此型号最终采用哪一路。

49.19 包 GPUInfoDLL.dll 的 SHA-256：
`7422ac0f7c8abb63bd57cf7b4b608410294628f1acf5a88b8a9f62cd0096648d`。
GetNVTemperature RVA 0x81f0 调用 RVA 0x2290，后者查询接口ID 0xe3640a56，
对应 NVIDIA 官方 NvAPI_GPU_GetThermalSettings；成功后复制 sensor[0].currentTemp，没有额外换算。
这一条 DLL 接口来自 NVIDIA 驱动，而非 EC VGAT；上层最终选路仍未知。
依据：[NVIDIA 接口表](https://github.com/NVIDIA/nvapi/blob/main/nvapi_interface.h)、
[温度结构定义](https://docs.nvidia.com/nvapi/nvapi_8h_source.html)。没有执行该 DLL。

FanInfo.GetEcCpuFanRpm/GetEcGpuFanRpm 仍是受保护的方法桩。
原厂第二风扇元数据为046c/046b，不能擅自改成046c/046d或套常见RPM公式。

先证明可重复的滞后，再讨论刷新延迟或风扇响应；本轮没有增加负载、改曲线或提高功耗。
