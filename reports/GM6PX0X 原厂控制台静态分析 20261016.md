## 已从包内确认的内容

`app/UniwillService/MyControlCenter/` 下包含服务程序及 ACPI DLL，
`UserFanTables/` 包含 Gaming、Office、Turbo 默认表和 M1T1 等用户表。
三张默认表各有 CPU/GPU 16 项，包含 UpT、DownT、Duty；其 Activated 均为 false。
这说明文件本身不能证明 Windows 或本机当前实际启用了这些曲线。

`Define.ECSpec` 的元数据常量如下。这里只记录符号和值，不把它们当作本机可用接口：

| 符号 | 地址 |
| --- | --- |
| ADDR_EC_MAIN_FAN_RPM_BYTE1 / BYTE2 | 0x0464 / 0x0465 |
| ADDR_EC_SECOND_FAN_RPM_BYTE1 / BYTE2 | 0x046c / 0x046b |
| ADDR_PROJECT_ID_BYTE | 0x0740 |
| ADDR_MAFAN_CONTROL_BYTE | 0x0751 |

特别注意：第二风扇 BYTE2 在这个包里确实是 **0x046b**，不能擅自改写为其他上游实现的
0x046d，也不能凭常量命名判定端序、换算系数或实际调用分支。

包内保留三套布局：`RamFan1_ECSpec`、`RamFan1p5_ECSpec`、`RamFan2_ECSpec`。
前两套 CPU 表从 0x0f00/0x0f10/0x0f20 开始，GPU 表从 0x0f30/0x0f40/0x0f50 开始。
第三套将同一区域组织为 F1/F2/F3 的 CPU/GPU 温度和 Duty 表；例如 0x0f50 在前两套中
为 GPU Duty，在第三套中却是 F2 CPU UpT。缺少机型分支时，直接写表可能写错含义。

原生 DLL 的导出表有 ReadEC、WriteEC、SMAPCTable、TempRead1/2/3 等。
ReadEC 的导出 RVA 为 0x3410，静态反汇编可见请求码 0x9c40a488；与
`MyECIO.AcpiCtrl.IOCTL_GPD_ACPI_ECREAD` 的十进制常量一致。
这证明包中有可继续追踪的通信实现，不代表 Windows IOCTL 可以直接用于 Linux。

## 还没解出的关键部分

`MyECIO.MyEcCtrl.GetProjectIdFromEC()` 等方法在磁盘原始 IL 中只有 11 字节的
`Runtime exception` 抛出占位，C# 反编译与 IL 核对一致。
模块初始化代码另有混淆和内存操作；目前尚未还原真实方法体，不能断言具体保护器或还原机制。
因此尚未确认：

- 本机 GM6PX0X 应选哪套风扇布局、哪个项目 ID 和能力位。
- Windows 控制台的 CPU/GPU 温度实际来源与刷新周期。
- 两个 RPM 字节的使用顺序及转速换算公式。
- 安全启用、自定义表提交、固件自动控制恢复的完整顺序。

Linux 当前 `R_UW_FAN_TEMP`/`R_UW_FAN_TEMP2` 读取 0x043e/0x044f，
`R_UW_FANSPEED`/`R_UW_FANSPEED2` 读取 0x1804/0x1809。
这些单字节风扇值不能直接命名成 RPM，也不能凭 Windows 常量替换现有读值。

本机 DSDT 已只读导出、经 iasl 反汇编。原始 AML SHA-256：
`de42c0d802ed746c1d032bf53ebb3b80f92172b8fb55e115b0e433566f542cda`。
这份本机固件明确给出：

- `\_SB.INOU.ECRR(addr)` 读取 `0xFE410000 + addr` 的一个字节。
- `ECMG` 中 `0x043e` 名为 CPTM，`0x044f` 名为 VGAT；另一字段 CPUT 位于 0x0e0d。
- 现有 WMI 路径经过 WMBC/OEMG/RKBC，以 EC 邮箱完成逻辑读操作；内部会写入命令邮箱，
  不能将其描述成物理总线层完全没有写操作。

临时、严格限定本机/BIOS 的 Linux 探针只调用 ECRR，没有 EC 写接口。
在当前内核 7.2.9-arch1-1 上编译、加载、10 次采样并卸载；随后公开工具最终版做了
3 次实机采样和访问权限验证。探针最后均已卸载，不注册 DKMS 或服务。
完整材料位于 `.local-tests/windows-oem/acpi-host/` 和 `ec-path-probe/`。

10 次初步样本中，ECRR CPU 温度全部等于前后两次 WMI 温度之一；GPU 温度也一致。
最终工具 3 次样本仍一致，但内部 CPU 温度与 EC 的差异仍明显：

| 样本 | CPU 内部温度 | EC CPU 温度 | 两种 EC 路径 |
| --- | --- | --- | --- |
| 1 | 91°C | 82°C | 一致 |
| 2 | 69°C | 81°C | 一致 |
| 3 | 81°C | 76°C | 一致 |

这缩小了调查范围：**本轮未复现 WMI 与内存路径的温度读值不一致**，
但没有证明传感器位置、刷新周期、平滑处理或 EC 固件策略正确。
三次样本不能量化温度滞后，也不能认定热尖峰问题已解决。

0x1804/0x1809 在 ECRR 路径始终为 255，而 WMI 路径为 128–170 等变化值。
说明至少这些高地址不能将两种访问路径直接互换。没有把这些字节当作 RPM。

另一个私有只读探针通过已安装驱动导出的 `uniwill_read_ec_ram()`，对 16 个固定低地址
逐项比较 WMI 与 ECRR，3 次采样均相等，随后卸载。得到以下新证据：

| 地址 | 观测值 | 有限解释 |
| --- | --- | --- |
| 0x0740 | 0x10 | 与现有驱动公开 model=16 对应，不能直接匹配 PH6 参数表 |
| 0x0765 / 0x0766 | 0xa1 / 0xb4 | 后者 bit 2 为 1，与当前驱动识别单区 RGB 的能力位一致 |
| 0x078e | 0xec | bit 6 为 1，与驱动 universal fan control 检测条件一致；不等于曲线已验收 |
| 0x0751 | 0x00 | 本次读取时没有开启 Windows 元数据中的 0x40 boost / 0x80 user fan 标志 |
| 0x0783–0x0786 | 全为 0 | 不能当作真实 CPU PL1/PL2/PL4 或温度限值；RAPL 55 W 不由它们证明 |
| 0x046b | 0x4b | 此短窗口恒定，不能靠 RPM 命名确认其用途 |
| 0x0464/0x0465、0x046c/0x046d | 部分字节变化 | RPM 候选仍需原厂显示/完整公式交叉验证 |

因此，单区 RGB 的判断增加了本机能力位证据，但没有由此宣称实体键盘绝无其他控制器。
同样，没有因风扇控制能力位为 1 就直接开启自定义曲线。

本轮从本机 MRO07 DSDT 的 SMRW 分支反推选择规则，然后只读核对运行值：

- `PPFG=4`，对应本机固件保存的阶段字段。
- EC `0x07d2` 的 GFID 为 `0x11`，Windows `Define.GN21_GPU_SKU` 元数据把 17 命名为 X4。
- `0x0751=0`，此刻没有启用原厂元数据中的 boost/user-fan 标志。
- 该 BIOS 的分支选择 **AX44**，其运行缓冲区是 `82 82 c8 05 00 19 57 7d ff ff ff ff`。

接着以 13 字节参数、固定 0xbb 读取标志，调用本机 `\_SB.INOU.SMRW`，只读偏移 0/4/8：

| 偏移 | 返回 DWORD（十六进制） |
| --- | --- |
| 0 | 05c88282 |
| 4 | 7d571900 |
| 8 | ffffffff |

按小端拼接三个 DWORD，与独立读取的命名缓冲区逐字节一致。
这验证了 **本机表选择与只读获取路径**，没有调用 0xaa 写分支。
SMRW 在当前固件中用到的参数字段覆盖 13 字节，因此探针不使用不足的短请求。
这里只验证 Linux 固定读请求；未认定 Windows 驱动的实际请求有缺陷。

官方 5.17.51.34 包的 UWACPIDriver.sys（46352 字节）SHA-256 为
`6e360ee4a0c42b2a4eaf46208c1592c87f8cd71aca2a6c52831a2ad356e61235`。

进一步把原厂 Windows 通信层与本机 ACPI 名称对上。没有加载或执行此 Windows 驱动。

Windows `Utility.SMAPCTABLE_STRUCT` 元数据的 9 个字节字段依次为 PL1、PL2、PL4、
TccOffset、ConfigurableTGP、DynamicBoost、TargetTemperature、DefaultTGP、DynamicBoostCpuTdp。
前几个原始字节为十进制 130/130/200/5，但结构体消费方法仍受保护，尚未证明该结构体
与这个 12 字节缓冲区的完整映射、各字段单位、PL4 编码或安全范围。
**不能把 130/130/200 当作本机已验收功耗上限，更不能覆盖当前 55 W 设置。**

## 继续核对 Windows 请求长度与 PL4 编码线索

本轮继续静态跟进 UWACPIDriver.sys，确认 RVA 0x2370 的 SMRW 请求构造函数：
