## 已从包内确认的内容

`app/UniwillService/MyControlCenter/` 下包含服务程序及 ACPI DLL，
`UserFanTables/` 包含 Gaming、Office、Turbo 默认表和 M1T1 等用户表。
三张默认表各有 CPU/GPU 16 项，包含 UpT、DownT、Duty；其 Activated 均为 false。
这说明文件本身不能证明 Windows 或本机当前实际启用了这些曲线。

`Define.ECSpec` 的元数据常量如下。这里只记录符号和值，不把它们当作本机可用接口：

| 符号 | 地址 |
| --- | --- |
| ADDR_EC_MAIN_FAN_RPM_BYTE1 / BYTE2 | 0x0464 / 0x0465 |
| ADDR_EC_SECOND_FAN_RPM_BYTE1 / BYTE2 | 0x046c / 0x046b |
| ADDR_PROJECT_ID_BYTE | 0x0740 |
| ADDR_MAFAN_CONTROL_BYTE | 0x0751 |

特别注意：第二风扇 BYTE2 在这个包里确实是 **0x046b**，不能擅自改写为其他上游实现的
0x046d，也不能凭常量命名判定端序、换算系数或实际调用分支。

包内保留三套布局：`RamFan1_ECSpec`、`RamFan1p5_ECSpec`、`RamFan2_ECSpec`。
前两套 CPU 表从 0x0f00/0x0f10/0x0f20 开始，GPU 表从 0x0f30/0x0f40/0x0f50 开始。
第三套将同一区域组织为 F1/F2/F3 的 CPU/GPU 温度和 Duty 表；例如 0x0f50 在前两套中
为 GPU Duty，在第三套中却是 F2 CPU UpT。缺少机型分支时，直接写表可能写错含义。

原生 DLL 的导出表有 ReadEC、WriteEC、SMAPCTable、TempRead1/2/3 等。
ReadEC 的导出 RVA 为 0x3410，静态反汇编可见请求码 0x9c40a488；与
`MyECIO.AcpiCtrl.IOCTL_GPD_ACPI_ECREAD` 的十进制常量一致。
这证明包中有可继续追踪的通信实现，不代表 Windows IOCTL 可以直接用于 Linux。

## 还没解出的关键部分

`MyECIO.MyEcCtrl.GetProjectIdFromEC()` 等方法在磁盘原始 IL 中只有 11 字节的
`Runtime exception` 抛出占位，C# 反编译与 IL 核对一致。
模块初始化代码另有混淆和内存操作；目前尚未还原真实方法体，不能断言具体保护器或还原机制。
因此尚未确认：

- 本机 GM6PX0X 应选哪套风扇布局、哪个项目 ID 和能力位。
- Windows 控制台的 CPU/GPU 温度实际来源与刷新周期。
- 两个 RPM 字节的使用顺序及转速换算公式。
- 安全启用、自定义表提交、固件自动控制恢复的完整顺序。

Linux 当前 `R_UW_FAN_TEMP`/`R_UW_FAN_TEMP2` 读取 0x043e/0x044f，
`R_UW_FANSPEED`/`R_UW_FANSPEED2` 读取 0x1804/0x1809。
这些单字节风扇值不能直接命名成 RPM，也不能凭 Windows 常量替换现有读值。
