## pkgrel5 settings failures: source qualification

The fifth patch closes the confirmed startup path with no prior in-memory settings: a malformed existing file was silently replaced by defaults, making fanControlEnabled true. An old reload could instead retain and overwrite with its prior settings. Both synchronous and asynchronous settings reads validate the types of present fields before consumers use them; for example, the string `"false"` is rejected instead of acting as true. Only `ENOENT` permits creation of defaults. Valid older settings with missing fields still use the existing migration, including the existing default `fanControlEnabled=true` when that field is absent. Unknown extension fields are retained. Keyboard members are checked only when present, preserving white-only devices that omit RGB values; this is a present-field guard rather than a complete schema or device-specific range policy.

The daemon separates read failures from migration and preserves the accumulated dirty flag when output-port synchronization returns false. Read, validation, port synchronization or migration-write failure restores the previous in-memory settings object and propagates the error. A first missing-file write failure leaves settings unavailable. This is limited to the synchronous settings-read/migration transaction: profile fallback, later profile mapping repair, runtime settings writes and D-Bus setters are unchanged. `writeFileSync` is not atomic, so an error after a partial disk write cannot promise disk rollback.
